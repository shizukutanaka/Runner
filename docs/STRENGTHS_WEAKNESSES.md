**作成日**: 2026-08-25 ／ **対象コミット**: `577b862` 以降

## この文書の読み方

かつて同名の分析文書（`ANALYSIS_STRENGTHS_WEAKNESSES.md`）が存在したが、
「GDPRコンプライアンス」「Circuit Breaker」など**実装が存在しない機能を長所として
列挙していた**ため削除された（経緯: `docs/SUPERSEDED_SUMMARIES.md`）。

本書はその置き換えである。守るルールは2つ:

1. **すべての主張に検証手段を付す。** 実測値・監査エントリ（`docs/FEATURE_AUDIT.md` のE番号）・
   再実行可能なコマンドのいずれかを引用する。引用できない主張は書かない
2. **期待値と実測値を混同しない。** 前任の文書群はこれを混同して負債になった

構成は、各節を**ソクラテス式の問い**で始め、**マスクの5段階**
（①要件を疑う → ②削除する → ③単純化する → ④高速化する → ⑤自動化する）で判定する。

## 問1: このプロダクトは何のために存在するか？

**答**: 個人〜小規模チームの配信者が、YouTube と Twitch のライブチャットを
一つの画面でモデレーションするため。

因果鎖は5段階: ①取り込み → ②判定 → ③プラットフォームへの反映 → ④人間のレビュー → ⑤記録。
セッション開始時点では**③が全経路で欠落**していた（判定してもYouTube/Twitchに何も起きない）。
現在は5段階すべてが実装・テストされている。

- ③の実装: YouTube 削除/BAN書き戻し（E-8, R-28）、Twitch AutoMod ALLOW/DENY（R-32）
- ④の実装: 保留キューUI + 構造化された理由バッジ（R-14）
- 検証: `backend/tests/integration/autoModWriteBack.test.js` ほか

**マスク判定**: 要件は本物（②〜④を欠いたモデレーションツールは製品として成立しない）。

## 短所 — 問3: どの間違いを選んだのか？

### 問3a: 誤検知と見逃し、どちらが高くつくか？

**答**: このプロダクトでは誤検知。無害な常連の発言を隠せばコミュニティが壊れ、
モデレーターの信頼も失う。見逃しは④（人間のレビュー）と通報で補える。

その選択の代償が最大の短所として現れている:

- **held-out recall 20%**（外部ベンチマーク・一度も調整に使っていない154件）。
  有害15件中12件を見逃す。これは実測値である（R-34〜R-36）
- 見逃しの内訳は「方針としてあえて拾わない」（バカ/だっさ等の軽口、政党批判）と
  「決定論の天井」（R-35のホールドアウト実験で+0ptを実測）に分かれる

### 問3b: なぜAI層で埋めないのか？

**答**: 埋める設計は済んでいるが、**OPENAI_API_KEY がこの環境に無く実測できていない**。
測定器だけが検証済み（W-3: `--no-ai` との差分で測る。`evaluationHarnessAi.test.js` 5件）。
**AI層の効果は現時点で未知**であり、既知であるかのように語らないこと。

| **✅ 解決（E-33）** フロントに死蔵コード検査が無かった | バックエンドには E-28 以来の検査があるのに、フロントには無かった。`src/api/` に**一度も import されない関数が29個（333行）**あり、画面が使うのは汎用の `updateSettings` 一本だった。削除して import 解析ベースの検査を追加した。名前の grep では `setTimezone` が他所の同名メソッドに一致して**未使用を見逃していた** |
| **✅ 解決（E-31）** 画面が中身を受け取っていなかった | 「フロントが読む項目が入っているか」の次に「**画面はそれを受け取っているか**」を問うた。`Dashboard.js` は `TriageQueue` に `pendingComments={[]}` という**空配列リテラルを直接書いていた**。サービスもAPIも画面側の300行も動くのに、入力が常に空なので待ち行列は永久に空だった。**呼び出し側が定数を渡していれば、サーバー側のガードは全て通過する**。取得済みコメントを渡すよう修正し、描画側と契約側の両方に検査を置いた |
| **✅ 解決（E-30）** 200を返すが中身が無い | 「500でないか」の次に「**フロントが読む項目が入っているか**」を問うた。監視ダッシュボードの「アプリケーション統計」は `comments.created_at` を読んでいたが、その列は無い（実体は `timestamp`）。テーブルは実在するのでE-29のガードは素通りしていた。**一度も表示されたことがない画面**だった。列単位の機械検査を追加した |
| **✅ 解決（E-29）** mount 済みで必ず500だったAPIが26件 | 「使われていないもの」を機械的に探す過程で、**未接続どころか接続済みで壊れているもの**が見つかった。実サーバーで `GET /api/users/timeouts/active` は SQLITE_ERROR で500——タイムアウトは配信のモデレーションで最も使う操作である。16件はテーブル・列を補って動くようにし、3件は実在するデータ源（winstonのログファイル、プロセス内メトリクス）へ繋ぎ替え、7件は要件から疑い直して削除した |
| **✅ 解決（E-27）** レートリミッターが2系統 | 実際に mount されていたのは8種のうち2種だけで、残りは参照0件だった（tier制限は削除済みの課金機構の遺物、`ddosProtection` は単一プロセスの50req/s）。使われている2つに縮小し、`RATE_LIMIT_ENABLED=false` でもログイン保護は常時有効という非対称を**意図的な仕様として明記**。実プロセスで 401×5→429 を実測 |

## 改善点 — 問4: 次の一手は何か？（優先度順）

1. **OPENAI_API_KEY を投入して W-3 を実測する**（所有者のみ可能）
   ```bash
   cd backend
   node src/scripts/evaluateModeration.js --no-ai   # 決定論層のみ
   node src/scripts/evaluateModeration.js           # AI層込み
   ```
   見るべきは held-out（`--split=test`）の recall と precision の変化。dev の数字は成果ではない
2. **Docker Hub に到達できる環境で `docker compose up -d --build`**（所有者のみ可能）
   ログイン→リアルタイム通知まで一周。ここまでのnginx/TLS/Cookie検証は実プロセスで済んでいる
3. **✅ 一部実施（2026-09-01）** — 実際に起きた障害の描画を固定した:
   `AnalyticsPanel.test.jsx`（実データ描画・`—`表示・デモ復活の禁止）、
   `HeldMessagesQueue.test.jsx`（バッジ7種）、`summaryRendering.test.jsx`（E-15）、
   `ModeratorDashboard.test.jsx`（操作が実APIを呼ぶこと・失敗を成功に見せないこと・
   固定値1,247を出さないこと）、`UserPanel.test.jsx`（未反映BANの明示）、`noFabricatedState.test.jsx`（**全コンポーネントを走査し、更新されない初期値＝飾りの数字を機械的に禁止**）。
   **この作業自体が E-26 を掘り当てた**——テストを書くために画面を読んだ結果、
   見出しの4つの数字が固定値で、履歴タブが架空の処罰3件だと分かった。
   **残り**: 未テストの画面の方が依然多い（Dashboard・Settings・監視・トリアージ・認証）。
   jsdomに `matchMedia` / `ResizeObserver` のポリフィルを入れたので、
   MUIコンポーネントの描画テストは今後書きやすくなっている
4. **✅ 実施済み（2026-09-01・E-27）** — レートリミッターの統一。
   ただし「寄せる」ではなく**削除**になった。8種のうち6種は一度も mount されておらず、
   `dynamicRateLimiter` の有料プラン優遇は削除済みの課金機構の遺物だった。
   ついでに `config.rateLimit.redisUrl` が存在せず、`RATE_LIMIT_STORE=redis` に
   すると `REDIS_URL` を無視して localhost に繋ぐ欠陥も見つかり修正した
5. **第2の外部ベンチマーク確保**: 現在の test 側は R-35/R-36 の報告で1回ずつ消費した。
   完全に未接触のセットがあれば、より強い一般化検証になる

**マスク判定**: 1と2は⑤（自動化・検証の完結）だが所有者の資源が要る。
3と4は③（単純化）——4は結果的に②（削除）だった。**「統一しよう」と思って開けたものの大半が、
統一する価値のない未使用コードだった**というのは本セッションで3度目である。

そして4度目に開けたとき（E-28→E-29）、**未使用の下に「使用中だが壊れている」層**が出てきた。
順序が逆だったことに注意したい。先に「動いているか」を疑っていれば、
26件が必ず500を返す状態にもっと早く気づけた。

さらに E-30 から E-33 まで、その下に四層あった。問いは毎回一段ずつ深くなっている:

| 問い | 見つかったもの | 機械検査 |
|------|----------------|----------|
| そのコードは呼ばれるか？ | 未使用45エクスポート・2,600行の到達不能コード | `deadExports.test.js` |
| 呼ばれるとして、落ちないか？ | 必ず500になる26エンドポイント | `missingTables.test.js` |
| 落ちないとして、中身はあるか？ | 200を返すが列が無く空の画面 | `sqlColumns.test.js` / `monitoringContract.test.js` |
| 中身があるとして、画面はそれを受け取るか？ | 空配列リテラルで固定されたトリアージ入力 | `Dashboard.test.jsx` / `insightsContract.test.js` |
| 受け取るとして、そのAPIは本当に何かしたか？ | 保存せず「Settings updated」を返すAPI | `stubImplementations.test.js` |
| フロント側に同じ規律はあるか？ | import されないAPI関数29個・333行 | `deadApiExports.test.js` |

**次の問いは「中身はあるとして、その数字は正しいか？」**である。
ここから先は実データと実クレデンシャルが要るため、所有者の環境でしか進められない。**新機能の追加は現時点で不要**——因果鎖は閉じており、
検知の広さは決定論では上がらないことを実測済み（R-35）。次の投資先はAI層の実測である。

## 問5: この文書自体はいつ嘘になるか？

数値を含む文書は必ず古くなる。本書の数値が現状と合っているかは:

```bash
cd backend && npx jest --silent                    # テスト数と成否
node src/scripts/evaluateModeration.js             # 自作セットの性能
# 外部ベンチマーク（上流を取得して --split=test で）: R-34 参照
```

**本書を更新するときは、実行した数値だけを書くこと。** 期待値を書きたくなったら
`docs/SUPERSEDED_SUMMARIES.md` を読み直すこと——同じ過ちで3,020行が削除された。
